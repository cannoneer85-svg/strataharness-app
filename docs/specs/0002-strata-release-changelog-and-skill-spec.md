# Спецификация 0002: Автогенерация списка изменений релиза и интерактивный скилл выпуска версий (`strata-release-changelog-and-skill`)

- **Статус триажа:** `ready-for-agent`
- **Категория:** `Development` / `Feature`
- **Фича:** `strata-release-changelog-and-skill`

## Problem Statement

Контур облачной сборки и атомарной публикации десктоп-приложения `StrataHarness` уже формирует в каждом выпуске `GitHub Releases` технический паспорт сборки (версию продукта из `Двухконтурного версионирования`, версию базового движка и `upstreamBaseTag`, ревизию встроенной методологии, матрицу статусов подписи платформ, инструкцию первого запуска для неподписанных сборок и таблицу контрольных сумм `SHA-256`).

Однако при подготовке реальных релизов для пользователей и мейнтейнера остаются два существенных пробела:

1. **Отсутствие истории изменений между релизами в карточке `GitHub Release`:** генератор релизных заметок не сравнивает выпускаемую версию с предыдущим `Релизным тегом продукта (strata-v*)` (или с базовым тегом движка `dsh-v*` для самого первого релиза `1.0.0`), не показывает дельту обновления движка и методологии и не поддерживает включение человекочитаемого продуктового резюме на русском языке, из-за чего карточка релиза содержит только технические метаданные и контрольные суммы без ответа на вопрос «что изменилось в этой версии».
2. **Ручная многошаговая рутина при выпуске новой версии:** чтобы выпустить новую версию продукта, мейнтейнеру приходится вручную вспоминать последовательность консольных команд (проверка чистоты дерева и отсутствия коллизии тега, выбор режима первого выпуска `1.0.0` без лишнего инкремента либо поднятие SemVer-версии, написание описания релиза, коммит, постановка тега `strata-v*` и отправка ветки вместе с тегом в `origin`), вместо единого управляемого скилла-мастера с защитными проверками.

## Solution

Релизный контур `StrataHarness` дополняется гибридным генератором истории изменений между релизами, подготовленным продуктовым резюме для первого выпуска `v1.0.0` и ручным интерактивным скиллом выпуска релизов `/strata-release`:

1. **Гибридное описание изменений в релизных заметках (русское продуктовое резюме + автоматический `What's Changed` из Git):** генератор релизных заметок автоматически подхватывает подготовленный версионный документ продуктового резюме на русском языке (если он присутствует для выпускаемой версии) и дополняет его автоматической секцией `What's Changed`, вычисленной по истории Git относительно предыдущего релиза. При отсутствии файла продуктового резюме (например, при прямом запуске сборки кнопкой `Run workflow` в веб-интерфейсе GitHub) сборка не прерывается, а мягко откатывается к публикации автоматической секции `What's Changed` с информационным предупреждением в лог сборки.
2. **Умный расчёт базовой ревизии (`baseline`) и фильтрация шума `Soft-Fork`:** для стабильного релиза базовой точкой сравнения выбирается последний по SemVer стабильный `Релизный тег продукта (strata-v*)` ниже выпускаемой версии, для пререлиза — последний любой `strata-v*` ниже выпускаемой версии, а для первого выпуска без предшествующих `strata-v*` — базовый тег движка `upstreamBaseTag`. При обновлении базового тега движка между релизами сотни транзитивных коммитов апстрима исключаются из поштучного списка и сворачиваются в одну агрегированную строку обновления движка (аналогично выводится дельта ревизии сабмодуля методологии), служебные коммиты поднятия релизной версии отфильтровываются, а продуктовые коммиты `StrataHarness` и `strata(override)` группируются по категориям с ограничением верхнего порога строк.
3. **CLI-предпросмотр истории изменений релиза:** релизный помощник получает отдельную подкоманду и корневой скрипт предпросмотра списка изменений для целевой версии до постановки тега, которую используют как разработчик, так и агентский скилл.
4. **Интерактивный ручной скилл `/strata-release` и готовое резюме релиза `v1.0.0`:** в реестр скиллов репозитория добавляется ручной скилл-мастер выпуска релиза с жёсткими проверками предзапуска (чистое рабочее дерево, отсутствие занятого тега `strata-v*` локально и в `origin`, поддержка выпуска ещё не тегированной текущей версии `1.0.0` без лишнего инкремента, остановка при нуле изменений после уже выпущенного тега), согласованием версии и русского продуктового резюме с пользователем, локальным коммитом, созданием тега `strata-v*` и отправкой в `origin` строго после явного подтверждения пользователя. Для первого релиза `v1.0.0` сразу подготавливается выверенное продуктовое резюме всех возможностей MVP.

## User Stories

1. Как пользователь, открывающий страницу релиза `StrataHarness` на GitHub, я хочу сразу под заголовком версии видеть понятное продуктовое резюме ключевых нововведений на русском языке, чтобы быстро понять ценность обновления без чтения сырой истории Git.
2. Как технический пользователь или ревьюер релиза, я хочу видеть в карточке каждого релиза автоматический раздел `What's Changed` с точной базовой точкой сравнения, дельтой базового движка и сабмодуля методологии, а также сгруппированным по категориям перечнем коммитов (`Features`, `Fixes`, `Engine & Desktop Overrides`, `CI & Tooling`, `Documentation & Other`), чтобы прозрачно отслеживать инженерные изменения между версиями.
3. Как пользователь первого релиза `StrataHarness v1.0.0`, я хочу, чтобы сравнение изменений первого выпуска автоматически велось от базового тега движка `dsh-v0.2.1-rc.4` и сопровождалось готовым продуктовым резюме всех четырёх фаз MVP (мульти-LLM бандл и пресеты методологии, брендированный интерфейс и онбординг, трёхуровневая изоляция десктопа, кроссплатформенный CI/CD и двухконтурное версионирование), чтобы первый релиз имел полноценное описание.
4. Как пользователь последующего стабильного релиза (например, `1.1.0` после промежуточных пререлизов `1.1.0-rc.1`), я хочу, чтобы список изменений стабильного выпуска сравнивался с предыдущим стабильным релизом `strata-v1.0.0`, а список изменений пререлиза — с ближайшим предшествующим тегом `strata-v*`, чтобы стабильный релиз отражал полную картину изменений с прошлой боевой версии.
5. Как мейнтейнер `Soft-Fork`, выпустивший новую версию после синхронизации с очередным тегом апстрима `dsh-v*`, я хочу, чтобы сотни чужих коммитов апстрима не затапливали описание нашего релиза, а сворачивались в одну сводную строку обновления движка с количеством коммитов апстрима, оставляя в детальном списке только наши продуктовые коммиты и `strata(override)`.
6. Как релиз-инженер, запустивший облачную сборку вручную через кнопку `Run workflow` без предварительного создания файла продуктового резюме для новой версии, я хочу, чтобы сборка не падала, а публиковала релиз с автоматически собранным разделом `What's Changed` из Git и понятным предупреждением в логе сборки.
7. Как разработчик, готовящий релиз в диалоге с агентом, я хочу вызвать одну ручную команду `/strata-release`, чтобы агент сам проверил готовность репозитория, показал изменения с прошлого релиза, предложил корректный номер версии и черновик русского резюме, подготовил релизный коммит с тегом `strata-v*` и отправил их в GitHub только после моего подтверждения.
8. Как разработчик, выпускающий самый первый релиз `1.0.0` (когда версия `1.0.0` уже записана в продуктовом манифесте, но тега `strata-v1.0.0` ещё не существует), я хочу, чтобы скилл `/strata-release` распознал невыпущенную текущую версию и предложил выпустить именно `1.0.0` без ошибочного инкремента до `1.0.1`.
9. Как разработчик, случайно вызвавший `/strata-release` при незакоммиченных файлах в рабочем дереве, при уже существующем теге `strata-v<версия>` в `origin` или при полном отсутствии новых коммитов после последнего выпущенного тега, я хочу, чтобы скилл немедленно остановился на этапе предварительной проверки и объяснил причину блокировки, не перезаписывая существующие теги и не смешивая незавершённую работу с релизным коммитом.
10. Как разработчик, работающий из терминала, я хочу иметь быструю команду предпросмотра списка изменений релиза, чтобы локально увидеть сгенерированный Markdown-блок `What's Changed` и статус подхвата русского резюме за секунду до постановки тега.

## Implementation Decisions

- **Хранение версионных продуктовых резюме в операционном контуре документации форка:** человекочитаемые резюме релизов размещаются в отдельном подкаталоге операционной документации `StrataHarness` по одному Markdown-файлу на версию (`v<semver>.md`) на русском языке с соблюдением правила «один абзац / пункт списка на одну физическую строку»; поскольку родительский каталог документации форка уже исключён из двуязычного англо-китайского спаривания, эти файлы проходят стандартные проверки валидности ссылок и переноса строк без требования китайских зеркал.
- **Контракт чтения и нормализации продуктового резюме:** генератор релизных заметок ищет файл продуктового резюме для целевой версии сборки; если файл существует и содержит непустой текст после очистки необязательного заголовка первого уровня (дублирующего заголовок релиза), его содержимое встраивается в раздел обзора релиза сразу после блока `Release Metadata`. Если файл отсутствует или пуст, генератор записывает предупреждение в диагностический поток и продолжает формирование заметок только с автоматической секцией `What's Changed`.
- **Алгоритм выбора базового тега сравнения (`baseline`):** резолвер базовой точки читает все локальные Git-теги с префиксом `strata-v`, валидирует их канонический SemVer и оставляет только версии строго меньше целевой версии сборки. Если целевая версия является стабильной (без пререлизного суффикса), выбирается максимальная по SemVer стабильная версия `strata-v*`; если целевая версия является пререлизом — выбирается максимальная любая версия `strata-v*` ниже целевой. Если подходящих тегов `strata-v*` нет (первый релиз) или целевой коммит совпадает с подготовкой первого выпуска, резолвер возвращает `upstreamBaseTag` из продуктового манифеста (при условии присутствия этого тега в Git-истории).
- **Сводка дельты двухконтурных зависимостей (движок и методология):** при сравнении `baseline` с целевой ревизией (`HEAD`) коллектор изменений читает продуктовый манифест и корневой `package.json` в обеих точках (для базового тега `dsh-v*`, где продуктового манифеста ещё не было, версией движка и тегом базы считается сам `dsh-v*`), а также сравнивает gitlink-хэш сабмодуля методологии. Если базовый тег движка обновился (`dsh-vA -> dsh-vB`), в подраздел платформенных обновлений `What's Changed` добавляется агрегированная строка обновления движка с точным числом коммитов апстрима между `dsh-vA` и `dsh-vB`; если изменился указатель сабмодуля методологии — добавляется строка обновления ревизии методологии (`revA -> revB`).
- **Фильтрация апстримных и служебных коммитов и категоризация изменений:** выборка коммитов строится по диапазону `baseline..targetRef` без merge-коммитов с исключением всех коммитов, достижимых из текущего `upstreamBaseTag` (`^<currentUpstreamBaseTag>`), благодаря чему при синхронизации с новым релизом апстрима сотни чужих коммитов ядра никогда не попадают в поштучный список изменений продукта. Дополнительно отфильтровываются технические релизные коммиты инкремента версии продукта (`chore(strata): bump product version...` и `chore(strata): prepare release...`). Оставшиеся коммиты распределяются в пять стабильных групп по conventional-префиксу: `Features` (`feat`), `Fixes` (`fix`, `perf`), `Engine & Desktop Overrides` (`strata(override)`), `CI & Tooling` (`ci`, `build`, `refactor`, `test`), `Documentation & Other` (`docs`, прочие). При превышении лимита в 50 отображаемых коммитов список усекается детерминированно с итоговой строкой `…and K more commit(s)`. Если между `baseline` и `targetRef` нет ни одного пользовательского коммита и ни одной дельты движка/методологии (например, повторная сборка того же состояния), выводится явная строка отсутствия функциональных изменений относительно `baseline`.
- **Подкоманда CLI предпросмотра изменений релиза:** релизный помощник дополняется подкомандой `changelog` (с поддержкой опциональных аргументов целевой версии, базового тега, целевой Git-ревизии и вывода в JSON либо Markdown) и соответствующим корневым npm-скриптом, чтобы агент и разработчик использовали единую детерминированную реализацию без дублирования Git-парсинга в промптах скилла.
- **Проектирование ручного скилла `/strata-release`:** скилл создаётся как строго ручной (`disable-model-invocation: true` и `allow_implicit_invocation: false`), размещается в разделе инфраструктуры и Git реестра скиллов под именем `strata-release` (не пересекаясь с зарезервированным шаблонным именем `release`), синхронизируется с зеркалом скиллов Claude и работает в четыре шага с двумя точками контроля:
  1. Предпроверка (`git status --short`, статус форка, проверка существования тега текущей продуктовой версии локально и в `origin` через `git ls-remote --tags origin`, запуск CLI-предпросмотра изменений с прошлого релиза; жёсткая остановка при грязном дереве или при нуле изменений после уже выпущенного тега).
  2. Согласование с пользователем через интерактивный инструмент вопросов: выбор версии (выпуск текущей невыпущенной версии без bump либо `patch` / `minor` / `major` / кастомный SemVer) и утверждение сгенерированного агентом черновика русского продуктового резюме.
  3. Локальная фиксация: обновление версии (если выбран инкремент), запись файла продуктового резюме, проверка локальных документационных гейтов на созданном файле, создание единого релизного коммита (если были изменены версия или файл резюме) и создание аннотированного или легковесного тега `strata-v<версия>` (с блокировкой при любой коллизии существующего тега).
  4. Отправка в удалённый репозиторий: показ точной команды `git push origin main strata-v<версия>` и выполнение пуша только после явного подтверждения пользователя на финальном запросе скилла (в полном соответствии с правилом запрета несанкционированного `git push`).
- **Оценка `minimal-diff` и зависимостей:** решение не добавляет ни одной новой внешней зависимости (используются штатный `node:child_process`, `node:fs` и уже установленный `semver`), переиспользует существующий модуль релизного помощника вместо создания отдельных пакетов или дублирующих парсеров Git-истории и укладывается в один продуктовый модуль плюс декларативный скилл и документацию.

## Testing Decisions

- **Принцип хороших тестов:** тестируется только внешне наблюдаемое поведение публичных функций и CLI релизного помощника на реальных временных Git-репозиториях (`git init`, реальные коммиты, теги `dsh-v*` и `strata-v*`), а также прохождение штатных валидаторов реестра скиллов и документации — без моков внутренних приватных функций.
- **Высокий шов тестирования (Seam):**
  1. Публичный API и CLI релизного помощника (`resolveReleaseBaselineTag`, `collectReleaseChangelog`, `generateReleaseNotes`, `collectReleaseArtifacts` и CLI-вызов `changelog` / `collect`).
  2. Репозиторные гейты целостности скиллов и документации (`Test-Template.ps1`, `verify-skill-invocation-metadata`, `verify-md-links`, `verify-md-wrap`).
- **Покрываемые сценарии и аналоги (Prior Art):** по образцу существующих интеграционных спецификаций `fork-ops` и `strata-workflows` на временных Git-репозиториях проверяются: первый релиз `1.0.0` от `dsh-v0.2.1-rc.4` с подхватом русского резюме; стабильный релиз `1.1.0` поверх промежуточного `1.1.0-rc.1` (выбор `strata-v1.0.0` как базы) и пререлиз `1.1.0-rc.2` (выбор `strata-v1.1.0-rc.1` как базы); синхронизация нового тега апстрима `dsh-v0.2.2` с исключением сотен апстримных коммитов из поштучного списка и выводом агрегированной строки `Engine upgraded`; фильтрация служебных bump-коммитов и усечение списка свыше 50 коммитов; мягкий фоллбэк без падения при отсутствии файла русского резюме; пустой диапазон при пересборке одного и того же коммита.

## Acceptance Criteria

1. `[auto]` При наличии файла русского продуктового резюме для выпускаемой версии `generateReleaseNotes` и `collectReleaseArtifacts` включают его содержимое в `RELEASE_NOTES.md` перед автоматической секцией `What's Changed`, а готовый файл резюме для `v1.0.0` присутствует в репозитории и проходит `verify-md-links` и `verify-md-wrap`.
2. `[auto]` При отсутствии или пустом файле продуктового резюме для выпускаемой версии `collectReleaseArtifacts` и CLI `changelog` не завершаются ошибкой, выводят предупреждение о фоллбэке и генерируют валидный `RELEASE_NOTES.md` с автоматической секцией `What's Changed`.

## Out of Scope

- Автоматический запуск инкремента версии `strata:version` внутри обычного закрытия рабочей задачи (`/close-task`).
- Вызов внешних LLM API изнутри CI-раннера GitHub Actions для генерации текста резюме на лету во время облачной сборки.
- Изменение матриц сборки установщиков Windows/macOS, логики подписи кода или формата статического фида `electron-updater`.
