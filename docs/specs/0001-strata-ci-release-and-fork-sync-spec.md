# Спецификация 0001: Кроссплатформенный CI/CD, двухконтурное версионирование, канал релизов и регламент сопровождения Soft-Fork (`strata-ci-release-and-fork-sync`)

- **Статус триажа:** `ready-for-agent`
- **Категория:** `Development` / `Epic`
- **Фича:** `strata-ci-release-and-fork-sync`

## Problem Statement

Десктоп-приложение StrataHarness уже изолировано от апстрима на трёх уровнях идентичности (`com.nikl.strataharness`, `@strata/desktop`, домашний каталог `~/.strataharness`, схема `strata://`, встроенный бандл методологии и мульти-провайдерный онбординг без облачной привязки и телеметрии DeepSeek) и успешно собирается локально под Windows `win-x64`.

Однако для промышленного выпуска кроссплатформенного продукта (Windows `.exe` + macOS `.dmg` и `.zip` для Apple Silicon и Intel) и долгосрочного сопровождения управляемого `Soft-Fork` остаются пять системных препятствий:

1. **Конфликт активных воркфлоу GitHub Actions с апстримом:** в активном каталоге воркфлоу унаследованы двадцать пять пайплайнов апстрима, одиннадцать из которых запускаются автоматически на события пулл-реквестов и задач, требуя внутренних раннеров, ботов и секретов DeepSeek; простое удаление этих файлов ломает контрактные тесты репозитория и порождает конфликты модификации/удаления при слиянии новых тегов `dsh-v*`.
2. **Отсутствие автономного кроссплатформенного пайплайна упаковки и подписи на стандартных GitHub-hosted раннерах:** апстримная сборка Windows умеет подписывать бинарники только физическим аппаратным USB-токеном SafeNet, неподписанная сборка macOS не генерирует архив `.zip` наряду с `.dmg`, а готовых модульных пайплайнов `StrataHarness` с режимом `unsigned` «из коробки» и бесшовным включением облачной подписи/нотаризации через секреты репозитория пока нет.
3. **Зависимость апстримной публикации от Tencent COS:** апстримная выгрузка артефактов и фидов автообновления завязана на внутренний бакет Tencent COS и префикс `dsh-desk`, тогда как `StrataHarness` требует открытой двухконтурной дистрибуции через `GitHub Releases` и vendor-agnostic статический `Канал автообновления (DOWNLOAD_PROD_ORIGIN)` с собственным префиксом `strataharness/feeds/<target>/`.
4. **Сцепленность версии продукта с внутренней версией движка:** внутренние ограничения монорепозитория требуют единой версии ядра (например, `0.2.1-rc.4`) более чем в ста манифестах `@deepseek-ai/dsh-*`, из-за чего без разделения контуров версий продукт вынужден либо показывать пользователям чужие RC-номера апстрима и терять возможность выпускать собственные минорные/патч-обновления на одной базе ядра, либо получать свыше ста конфликтов слияния при каждом обновлении `dsh-v*`.
5. **Отсутствие автоматизированного контроля инвариантов `Soft-Fork` и мониторинга релизов апстрима:** системному архитектору нужен детерминированный CLI-инструмент проверки изоляции точек `strata(override)` и автоматический `Радар апстрима (strata-upstream-watch)`, отслеживающий выход новых тегов `dsh-v*` и формирующий оценку влияния на переопределения форка без каких-либо фоновых проверок внутри клиентского приложения конечного пользователя.

## Solution

Внедряется завершённый контур релизной инженерии, дистрибуции и сопровождения `Soft-Fork` для десктоп-приложения `StrataHarness`:

1. **Двухконтурное версионирование (`strata-product.json`):** вводится корневой продуктовый манифест с собственной линейкой классического SemVer начиная с `1.0.0` (`+1 MINOR` — продуктовые фичи и синхронизации с `upstream`, `+1 PATCH` — багфиксы и обновления методологии, `+1 MAJOR` — крупные архитектурные вехи). Продуктовая версия управляет именами установщиков (`strataharness-1.0.0-...`), версией приложения Electron (`app.getVersion()`), сравнением версий `electron-updater`, клиентским Web UI, пакетами `@strata/*` и тегами `strata-v*`, тогда как семейство пакетов ядра `@deepseek-ai/dsh-*` сохраняет нативную версию базового тега `dsh-v*` без конфликтов слияния. В окне «О программе» (`About StrataHarness`), в `GitHub Release Notes` и в диагностике форка справочно выводится строка базового движка (`Engine: DSH <версия>`).
2. **Бесконфликтная изоляция воркфлоу апстрима:** все двадцать пять апстримных YAML-пайплайнов переносятся побайтово без правок содержимого в изолированный архивный каталог внутри `.github/`, а ссылки в апстримных контрактных тестах точечно перенаправляются (`strata(override)`), оставляя активный каталог GitHub Actions исключительно за пайплайнами `strata-*.yml` и сохраняя 100%-ный `rename-tracking` при будущих `git merge dsh-v*`.
3. **Модульные кроссплатформенные пайплайны GitHub Actions и режимы подписи `auto` / `unsigned` / `signed`:** создаются переиспользуемые пайплайны сборки Windows (`win-x64` `.exe` на `windows-2022`) и macOS (`mac-arm64` и `mac-x64` `.dmg` + `.zip` на Apple Silicon `macos-15` с Rosetta 2) с рекурсивной инициализацией сабмодуля методологии и кэшированием зависимостей, а также оркестратор релиза по пушу `Релизного тега продукта (strata-v*)` и ручному запуску. В режиме `auto` при отсутствии сертификатов сборка чисто откатывается в `unsigned` (артефакты с суффиксом `-unsigned`, включая `.dmg` и `.zip` на macOS, без публикации `latest*.yml`); при добавлении секретов Apple Developer ID / App Store Connect и стандартного `.pfx`-сертификата Windows (с fallback-цепочкой RFC-3161 TSA серверов времени наряду с поддержкой локального аппаратного токена SafeNet) активируется полноценная подпись и нотаризация без изменения кода пайплайнов.
4. **Атомарная публикация в `GitHub Releases` и `Канал автообновления (DOWNLOAD_PROD_ORIGIN)`:** релизный оркестратор собирает матрицу платформ с сохранением диагностических логов и готовых сборок при частичном сбое (`fail-fast: false`), но блокирует публикацию боевого релиза до успеха всех трёх целевых платформ (`win-x64`, `mac-arm64`, `mac-x64`), формирует контрольные суммы `SHA256SUMS.txt` и структурированные Release Notes, а для подписанных сборок при заданном `DOWNLOAD_PROD_ORIGIN` формирует и (при наличии S3-совместимых секретов) автоматически синхронизирует статический HTTPS-фид `strataharness/feeds/<target>/` без участия Tencent COS.
5. **Единый CLI сопровождения `Soft-Fork` и `Радар апстрима (strata-upstream-watch)`:** создаются единый инструмент управления форком (статус версий, атомарный бамп продуктовой версии, обновление сабмодуля методологии, жёсткий аудит инвариантов изоляции и гигиены воркфлоу, подготовка ветки слияния с отчётом по `upgrade-guide`), эксплуатационный ранбук на русском языке и ежедневный фоновый воркфлоу-радар для системного архитектора, создающий/обновляющий единый дедуплицированный GitHub Issue (и опциональный webhook-алерт) при выходе новых тегов `dsh-v*`.

## Implementation Decisions

### 1. Двухконтурное версионирование продукта и ядра

- В корне репозитория вводится декларативный JSON-манифест продукта со следующей схемой данных:

```json
{
  "productName": "StrataHarness",
  "productVersion": "1.0.0",
  "upstreamBaseTag": "dsh-v0.2.1-rc.4",
  "upstreamRepository": "https://github.com/deepseek-ai/deepseek-harness.git"
}
```

- Корневой манифест монорепозитория и все пакеты семейства `@deepseek-ai/dsh` / `@deepseek-ai/dsh-*` (включая хост-оболочку Electron) сохраняют версию базового тега апстрима (`0.2.1-rc.4`), благодаря чему штатная проверка целостности воркспейса и сборка встроенного дерева пакетов `dsh` проходят без ослабления правил и без конфликтов при будущих `git merge dsh-v*`.
- Собственные пакеты пространства `@strata/*` синхронизируются с полем `productVersion` (`1.0.0+`).
- Слой конфигурации упаковки десктопа читает `productVersion` из продуктового манифеста (с поддержкой явного переопределения через переменную окружения для тестовых прогонов апдейтера `1.0.0 → 1.0.1`) и передаёт её в `extraMetadata.version` сборщика Electron, а версию ядра — в дополнительное поле метаданных `extraMetadata.dshEngineVersion`. В результате `app.getVersion()`, имена установщиков (`strataharness-<productVersion>-<os>-<arch><suffix>.<ext>`), манифесты `latest.yml` / `latest-mac.yml` и проверка тегов `strata-v<productVersion>` работают строго в продуктовой SemVer-шкале, тогда как упакованный рантайм `dsh` внутри `app.asar` сохраняет нативную версию движка и проходит все проверки `afterPack` и `check:package`.
- Сборщик окружения клиентского Web UI использует `productVersion` из продуктового манифеста в качестве отображаемой клиентской версии по умолчанию (если переменная `DSH_CLIENT_VERSION` не переопределена явно извне), а нативное окно «О программе» (`About StrataHarness`) дополняется справочной строкой версии базового движка (`Engine: DSH <dshEngineVersion>`).

### 2. Изоляция апстримных GitHub Actions воркфлоу

- Все двадцать пять апстримных YAML-файлов воркфлоу переносятся через `git mv` в архивный подкаталог внутри `.github/` побайтово без единого изменения содержимого. Побайтовая идентичность критична по двум причинам: во-первых, внутренние строковые ссылки между апстримными воркфлоу проверяются существующими контрактными тестами репозитория как литералы; во-вторых, стратегия слияния Git `ort` распознаёт 100%-ное совпадение при переименовании и автоматически применяет будущие апстримные правки к перенесённым файлам.
- В апстримных тестовых наборах воркфлоу и вспомогательных скриптах проверки ревью обновляется только константа пути к каталогу апстримных воркфлоу (точечная правка категории `strata(override)`).
- В активном каталоге воркфлоу GitHub Actions разрешены исключительно файлы с префиксом `strata-*.yml`; нарушение этого инварианта (например, появление нового файла воркфлоу при слиянии свежего тега апстрима) блокируется как контрактным тестом, так и аудитором `Soft-Fork`.

### 3. Архитектура CI/CD пайплайнов, подписи кода и дистрибуции

- Создаются четыре модульных воркфлоу:
  1. **Пайплайн упаковки Windows (`win-x64`):** раннер `windows-2022`, таймаут 90 минут, триггеры `workflow_dispatch` и `workflow_call`, рекурсивный `checkout` с поддержкой токена доступа к сабмодулю методологии (`STRATA_SUBMODULE_TOKEN` с откатом на стандартный токен запуска), кэширование `pnpm store`, скачанных архивов `primary-runtime` и кэша Electron, обязательные проверки ограничений воркспейса, сборка артефактов, упаковка NSIS `.exe` и верификация `check:package` с выгрузкой диагностического каталога `packaging-runs/` в `if: always()`. На Windows-раннере в шагах сборки явно гарантируется приоритет системного `System32` (`bsdtar`) над `Git\usr\bin`.
  2. **Пайплайн упаковки macOS (`mac-arm64`, `mac-x64`):** раннер Apple Silicon `macos-15` (с автоматической установкой Rosetta 2 для кросс-таргета `mac-x64`), таймаут 120 минут, матрица из двух архитектур с `fail-fast: false`, триггеры `workflow_dispatch` и `workflow_call`, выпуск одновременно `.dmg` и `.zip` как в `signed`, так и в `unsigned` режимах, верификация `check:package` и сохранение логов `packaging-runs/` в `if: always()`.
  3. **Оркестратор релиза (`strata-release`):** запускается автоматически по пушу тега `strata-v*` и вручную через `workflow_dispatch`; выполняет быстрый `preflight` (проверка совпадения версии тега с продуктовым манифестом и инициализации сабмодуля методологии), вызывает пайплайны Windows и macOS с правами `contents: read`, а в финальном джобе публикации (с правами `contents: write` только на этом шаге) проверяет атомарное наличие артефактов всех трёх платформ (`win-x64`, `mac-arm64`, `mac-x64`) для стабильного релиза, формирует единый `SHA256SUMS.txt` и Release Notes (с версией продукта, базой `dsh-v*`, ревизией методологии и памяткой Gatekeeper / SmartScreen для `unsigned` сборок), публикует `GitHub Release`, всегда сохраняет архив статического фида `update-feed` в артефактах запуска и при наличии секретов `STRATA_S3_*` синхронизирует фид в S3-совместимый бакет через штатный AWS CLI раннера. Выбор подмножества таргетов разрешён исключительно при ручном запуске с флагом `draft` или `prerelease`.
  4. **Фоновый радар апстрима (`strata-upstream-watch`):** запускается по ежедневному расписанию `cron` и вручную через `workflow_dispatch` (никогда не встраивается в клиентский код `StrataHarness`); опрашивает удалённые теги `dsh-v*` официального репозитория апстрима, сравнивает их с `upstreamBaseTag` в продуктовом манифесте и при обнаружении более свежих версий вызывает генератор Impact-отчёта, идемпотентно создавая или обновляя единственный открытый GitHub Issue с меткой радара (без спама дубликатами) и при наличии `STRATA_ARCHITECT_WEBHOOK_URL` отправляя краткую сводку в webhook архитектора.

- **Таблица состояний подписи и канала автообновления (`signing_mode` × секреты × `DOWNLOAD_PROD_ORIGIN`):**

| Входной режим | Секреты сертификатов платформы | `DOWNLOAD_PROD_ORIGIN` | Результирующий режим | Выходные артефакты | Генерация фида `latest*.yml` |
|---|---|---|---|---|---|
| `auto` | Отсутствуют или неполные | Любой | `unsigned` | `.exe`, `.dmg`, `.zip` с суффиксом `-unsigned` | Отключена (`publish: null`) |
| `auto` | Полный комплект | Не задан | `signed` | Подписанные `.exe`, `.dmg`, `.zip` (нотаризованные на macOS) | Отключена (`publish: null`) |
| `auto` | Полный комплект | Задан (`https://...`) | `signed` | Подписанные `.exe`, `.dmg`, `.zip` | Включена (`${DOWNLOAD_PROD_ORIGIN}/strataharness/feeds/<target>/`) |
| `unsigned` | Любые | Любой | `unsigned` | `.exe`, `.dmg`, `.zip` с суффиксом `-unsigned` | Отключена (`publish: null`) |
| `signed` | Отсутствуют или неполные | Любой | **Ошибка `preflight` (fail-fast)** | Сборка не стартует | — |
| `signed` | Полный комплект | Задан / не задан | `signed` | Подписанные `.exe`, `.dmg`, `.zip` | Включена при заданном HTTPS URL, иначе `publish: null` |

- **Адаптер облачной подписи Windows и защита секретов:** модуль подписи Windows расширяется поддержкой стандартного файлового или Base64-кодированного сертификата `.pfx` (`WIN_CSC_LINK`, `WIN_CSC_KEY_PASSWORD`) наряду с существующим режимом аппаратного токена SafeNet (выбор режима явный по наличию конфигурации `.pfx`, без ломающих изменений для локальной аппаратной подписи). При вызове `signtool.exe` для штампа времени используется последовательный fallback по списку RFC-3161 TSA серверов (`http://timestamp.digicert.com`, `http://timestamp.sectigo.com`, `http://timestamp.globalsign.com/tsa/r6advanced1`) с контролируемыми паузами между попытками. Любые временные файлы ключей и сертификатов в CI создаются только внутри `RUNNER_TEMP`, их значения регистрируются через маскирование логов, а удаление файлов выполняется в обязательном шаге `if: always()`.
- **Префикс пути статического фида автообновления:** внутренний префикс пути фида автообновлений и плана выгрузки переводится с апстримного `dsh-desk` на `strataharness/feeds` (`${DOWNLOAD_PROD_ORIGIN}/strataharness/feeds/<target>/`), при этом блокировка доменов `download.deepseek.com` и `*.deepseek.com` остаётся безусловной как на этапе сборки, так и в рантайме.

### 4. Автоматизация сопровождения `Soft-Fork` и эксплуатационная документация

- Создаётся единый CLI-инструмент сопровождения форка с шестью подкомандами, выведенными в скрипты корневого манифеста:
  - `strata:status` — сводка продуктовой версии, базового тега `dsh-v*`, версии ядра, состояния сабмодуля методологии, числа коммитов `strata(override)` поверх базы и статуса рабочего дерева;
  - `strata:version` — атомарное обновление `productVersion` (`major`, `minor`, `patch` или явная SemVer-строка) и опционально `upstreamBaseTag` в продуктовом манифесте и всех пакетах `@strata/*` с валидацией SemVer;
  - `strata:update-methodology` — контролируемое переключение/обновление сабмодуля методологии до указанного тега или ветки с проверкой целостности точки входа методологии;
  - `strata:audit-overrides` — детерминированная проверка всех архитектурных инвариантов `Soft-Fork`: трёхуровневая изоляция десктопа (`com.nikl.strataharness`, `@strata/desktop`, `~/.strataharness`, `strata://`), подключение `@strata/product-bundle`, отсутствие запрещённых URL `download.deepseek.com`, совпадение версий между продуктовым манифестом и `@strata/*`, непустой сабмодуль методологии и наличие в активном каталоге GitHub Actions только файлов `strata-*.yml`;
  - `strata:check-upstream` — опрос доступных тегов `dsh-v*` (из локального `upstream` remote или переданного URL репозитория), сравнение с `upstreamBaseTag`, формирование структурированного JSON и Markdown Impact-отчёта (список новых тегов, добавленных документов `upgrade-guide` при наличии локально скачанных объектов и пересечений изменённых апстримом файлов со списком файлов, затронутых коммитами `strata(override)`);
  - `strata:prepare-upstream-sync` — проверка чистоты рабочего дерева Git (жёсткий отказ при незакоммиченных изменениях), fetch тегов `upstream`, создание ветки синхронизации `sync/<tag>`, вывод Impact-отчёта и чеклиста пятишагового регламента слияния.
- Эксплуатационный ранбук сопровождения `Soft-Fork` размещается в выделенном подкаталоге `docs/strata/` на русском языке; этот подкаталог регистрируется в списке операционных документов репозитория и исключений манифеста EN/ZH перевода, чтобы продуктовые проверки двуязычной документации (`test:docs` / `doc-sync`) проходили штатно без требования китайской копии для внутренних операционных регламентов `StrataHarness`.

### 5. Оценка объёма решения и дисциплина `minimal-diff`

- **Ноль новых внешних npm-зависимостей:** все задачи решаются стандартной библиотекой Node.js (`node:fs`, `node:path`, `node:child_process`, `node:crypto`, `node:http`), уже установленными в воркспейсе пакетами (`semver`, `js-yaml`, `electron-builder`, `electron-updater`, `vitest`) и штатными утилитами стандартных образов GitHub-hosted раннеров (`git`, `gh`, `aws`, `signtool.exe`, `xcrun`).
- **Отказ от избыточных абстракций:** мы не создаём собственный HTTP-сервер обновлений, кастомный S3 SDK-клиент в рантайме или сложные обёртки вокруг `electron-builder` — вместо этого переиспользуем штатный `provider: generic` в `electron-updater`, существующий конвейер упаковки и существующий локальный квалификационный стенд автообновления, ограничивая дифф в файлах апстрима минимальными точками `strata(override)` и вынося всю новую логику релизной инженерии в собственные файлы `strata-*`.

## Testing Decisions

Хороший тест проверяет внешне наблюдаемое поведение и контракты на максимально высоком уровне интеграции (выходы CLI, сгенерированную конфигурацию сборщика, структуру YAML-пайплайнов и реальный цикл обновления упакованного Electron-приложения), не привязываясь к приватным вспомогательным функциям.

Проверка решения опирается на **четыре шва тестирования (Testing Seams)**, три из которых напрямую переиспользуют уже существующую тестовую инфраструктуру репозитория:

1. **Шов 1 — Поведенческий CLI-шов инструмента сопровождения `Soft-Fork` (новый модульный шов верхнего уровня):**
   - Тестирует команды `status`, `version`, `audit-overrides`, `check-upstream`, `prepare-upstream-sync` и `update-methodology` на изолированных временных фикстурах Git-репозиториев и файловых деревьев.
   - Проверяет как позитивные сценарии (бамп SemVer `1.0.0 → 1.1.0`, чистый аудит, обнаружение нового тега `dsh-v*` с пересечением по файлам `strata(override)` и новым `upgrade-guide`), так и негативные сценарии (грязное Git-дерево, появление постороннего `.yml` в активном каталоге воркфлоу, нарушение `appId` или запрещённый домен апстрима, невалидный SemVer).
   - *Prior art:* существующие Vitest-спеки скриптов верификации репозитория в корневом каталоге скриптов.
2. **Шов 2 — Контрактный YAML-шов воркфлоу GitHub Actions (переиспользование существующего шва):**
   - Все существующие апстримные Vitest-спеки воркфлоу прогоняются без ослабления проверок против перенесённого архивного каталога апстримных пайплайнов.
   - Новый Vitest-набор для пайплайнов `strata-*.yml` проверяет: отсутствие любых не-`strata-*.yml` файлов в активном каталоге воркфлоу, наличие триггеров `workflow_dispatch` / `workflow_call` / `strata-v*` / `schedule`, рекурсивную инициализацию сабмодулей, права `contents: read` на сборке и `contents: write` только на публикации, привязку входных параметров через `env:`, атомарный гейт трёх платформ перед релизом и наличие `if: always()` очистки временных сертификатов.
   - *Prior art:* существующие контрактные тесты воркфлоу упаковки Windows, macOS и публикации десктопа.
3. **Шов 3 — Конфигурационный шов упаковки, двухконтурных версий и подписи десктопа (переиспользование существующего шва):**
   - Проверяет публичные функции генерации конфигурации `electron-builder`, окружения автообновления, плана выгрузки фида, клиентской версии Web UI и адаптера подписи Windows.
   - Подтверждает разделение `productVersion` (`1.0.0`) и версии ядра (`0.2.1-rc.4`), выпуск `['dmg', 'zip']` на macOS в `unsigned` режиме, формирование пути фида `${DOWNLOAD_PROD_ORIGIN}/strataharness/feeds/<target>/`, матрицу `auto` / `unsigned` / `signed` и fallback-цепочку RFC-3161 TSA серверов при сбое первого штампа времени (через инъекцию исполнителя команды `signtool` без требования физического сертификата в unit-тесте).
   - *Prior art:* существующие unit-тесты окружения клиентской сборки и конфигурации десктоп-пакета.
4. **Шов 4 — Интеграционный квалификационный шов автообновления упакованного Electron-приложения (`check:package` + `test:updates:local`, существующий E2E-шов):**
   - Запускает реальный упакованный бинарник `StrataHarness` на Windows против локального HTTP-сервера обновлений, проверяя валидность упакованного `app.asar`, изоляцию `~/.strataharness`, чтение продуктовой версии `app.getVersion()` и полный цикл обнаружения и загрузки новой версии через `electron-updater`.
   - *Prior art:* существующий локальный квалификационный стенд автообновления десктоп-приложения.

## Acceptance Criteria

1. `[auto]` В корне репозитория присутствует валидный продуктовый манифест с продуктовой версией `1.0.0` и базовым тегом `dsh-v0.2.1-rc.4`; версии всех пакетов `@strata/*` равны `1.0.0`, тогда как версии корневого манифеста монорепозитория и всех пакетов `@deepseek-ai/dsh-*` остаются равными версии ядра и проходят штатную проверку ограничений воркспейса (`pnpm run constraints`).
2. `[auto]` Генератор конфигурации `electron-builder`, сборщик окружения клиентского Web UI (`DSH_CLIENT_VERSION`), `app.getVersion()` упакованного приложения и шаблоны имён установщиков используют продуктовую версию (`1.0.0`), а метаданные встроенного рантайма `dsh` внутри `app.asar` сохраняют версию ядра (`0.2.1-rc.4`), успешно проходя `check:package`.
3. `[auto]` Диалог «О программе» (`About StrataHarness`), генератор `GitHub Release Notes` и команда `pnpm run strata:status` отображают как продуктовую версию `StrataHarness`, так и справочную строку версии базового движка `DSH`.
4. `[auto]` Все двадцать пять апстримных воркфлоу перенесены побайтово без изменений содержимого в изолированный каталог `.github/upstream-workflows/`, в активном каталоге `.github/workflows/` присутствуют только файлы `strata-*.yml`, и все существующие контрактные Vitest-тесты апстримных воркфлоу проходят на 100%.
5. `[auto]` Воркфлоу упаковки Windows (`win-x64`) и macOS (`mac-arm64`, `mac-x64`) поддерживают `workflow_dispatch` и `workflow_call`, выполняют `actions/checkout` с рекурсивной инициализацией сабмодуля методологии, кэшируют зависимости и архивы рантайма, исполняются с минимальными правами `contents: read`, передают все `inputs` через `env:` и выгружают логи `packaging-runs/` в шаге `if: always()`.
6. `[auto]` В режиме подписи `auto` при отсутствии секретов сертификатов сборка автоматически переключается в `unsigned` (`publish: null`, без `latest*.yml`) и конфигурирует выпуск `.exe` на Windows и одновременно `.dmg` + `.zip` на macOS с суффиксом `-unsigned`; при явно запрошенном режиме `signed` и отсутствии обязательных секретов `preflight`-проверка завершается немедленной ошибкой с перечислением недостающих переменных.
7. `[auto]` В режиме `signed` без заданного `DOWNLOAD_PROD_ORIGIN` конфигурация упаковки разрешает выпуск подписанных установочных пакетов с `publish: null`, а при заданном HTTPS `DOWNLOAD_PROD_ORIGIN` формирует URL статического фида `${DOWNLOAD_PROD_ORIGIN}/strataharness/feeds/<target>/` без каких-либо ссылок на Tencent COS, `dsh-desk`, `download.deepseek.com` или `*.deepseek.com`.
8. `[auto]` Модуль подписи Windows поддерживает подпись через `.pfx` (`WIN_CSC_LINK`, `WIN_CSC_KEY_PASSWORD`) с последовательным fallback-перебором минимум трёх RFC-3161 TSA серверов при транзиентной ошибке штампа времени, сохраняет поддержку аппаратного токена SafeNet, а пайплайны CI материализуют временные файлы ключей только в `RUNNER_TEMP` с маскированием и гарантированным удалением в `if: always()`.
9. `[auto]` Оркестратор релиза по тегу `strata-v*` блокирует запуск на этапе `preflight`, если версия тега не совпадает с `productVersion` продуктового манифеста или сабмодуль методологии пуст, запускает сборку платформ с `fail-fast: false`, требует наличия артефактов всех трёх платформ (`win-x64`, `mac-arm64`, `mac-x64`) для публикации стабильного релиза (разрешая неполный набор таргетов только для ручного `draft` / `prerelease`), генерирует `SHA256SUMS.txt`, сохраняет архив `update-feed` и при наличии `STRATA_S3_*` синхронизирует фид через AWS CLI.
10. `[auto]` На локальной Windows-машине упакованный дистрибутив `StrataHarness` успешно проходит как `check:package`, так и полный локальный квалификационный интеграционный тест автообновления `test:updates:local` (переход между двумя продуктовыми версиями поверх локального HTTP-сервера с полной изоляцией профиля `~/.strataharness`).
11. `[auto]` CLI сопровождения `Soft-Fork` (`strata:status`, `strata:version`, `strata:update-methodology`, `strata:audit-overrides`, `strata:check-upstream`, `strata:prepare-upstream-sync`) покрыт автотестами Vitest: `strata:version` атомарно обновляет продуктовый манифест и пакеты `@strata/*`, `strata:audit-overrides` детектирует нарушение любого инварианта изоляции или посторонний файл в `.github/workflows/`, `strata:prepare-upstream-sync` блокируется на грязном Git-дереве, а `strata:check-upstream` формирует Impact-отчёт по новым тегам `dsh-v*`, `upgrade-guide` и пересечениям с коммитами `strata(override)`.
12. `[auto]` Воркфлоу `strata-upstream-watch` настроен на ежедневный запуск по расписанию и `workflow_dispatch`, использует `strata:check-upstream` для идемпотентного создания/обновления одного открытого GitHub Issue без создания дубликатов, поддерживает опциональный webhook `STRATA_ARCHITECT_WEBHOOK_URL` и никак не затрагивает клиентский рантайм приложения.
13. `[auto]` Русскоязычный эксплуатационный ранбук сопровождения `Soft-Fork` и выпуска релизов создан в `docs/strata/`, исключён из требования китайского перевода, и все документационные и сборочные проверки репозитория (`pnpm run test:docs`, `pnpm run build`) проходят без ошибок и без упоминания сырых SHA коммитов в отслеживаемых файлах.
14. `[manual]` После подключения удалённого репозитория GitHub `origin` тестовый запуск `workflow_dispatch` в режиме `auto` (без платных сертификатов) собирает рабочие `unsigned`-установщики Windows `.exe` и macOS `.dmg` + `.zip`, а во вкладке GitHub Actions отображаются только четыре собственных воркфлоу `StrataHarness`.

## Out of Scope

- Сборка и дистрибуция пакетов под Linux (`.AppImage`, `.deb`, `.rpm`) и Windows `arm64` в рамках текущего MVP (поддерживаются `win-x64`, `mac-arm64`, `mac-x64`).
- Закупка и выпуск юридических сертификатов Apple Developer Program и Windows OV/EV Code Signing, а также внешняя регистрация DNS-домена и облачного S3/CDN аккаунта (реализуется полная программная и CI-готовность, активируемая добавлением секретов).
- Любые проверки обновлений апстрима `DeepSeek Harness`, телеметрия или упоминания апстрим-релизов внутри пользовательского интерфейса клиентского приложения `StrataHarness`.
- Изменение версий внутренних пакетов ядра `@deepseek-ai/dsh-*` или модификация бизнес-логики агентного цикла `agent-loop`.
